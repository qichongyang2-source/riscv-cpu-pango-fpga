**15/15 通过。** 说明：

- t08 的周期数主要来自"关中断后再空转 2000 次"的负向验证。
- 加入 Cache 后，小程序的周期数比无 Cache 版本增加，增量正是**冷缺失**代价
  （每行约 5 拍）。以 t01 为例：131 条指令约 35 个 16 B 行，35×5≈175 拍，
  与实测增量吻合。
- t10 验证了 Cache 的实际收益：15989 次取指只缺失 15 次（顺序代码一次性装入），
  D-Cache 在 1089 次命中之外产生 257 次容量缺失（4 KB 数据 > 2 KB Cache），
  符合 2 KB 容量的预期。
- t11 验证两路组相联：两个相隔 2 KB 的数组交替访问，D-Cache 仅 2 次冷缺失、
  128 次命中；若为直接映射，两者会争用同一组，几乎每次访问都缺失。
- BTB 效果：t08 的等待循环 IPC 0.59→0.98，t10 0.72→0.91，t06 0.61→0.70。
- t13 验证了本轮的异常/中断补全：向量 mtvec、外部中断（mcause 0x8000_000B）、
  非对齐 load/store（mcause 4/6）、WFI 按 NOP 执行。
- 真实基准（CoreMark）的循环体会反复使用同一批行，冷缺失被摊薄，
  Cache 的主要价值在于让 64 KB 存储器可以用 BRAM 实现，从而提升可综合频率。

## 4. 验证过程中发现并修复的问题

| # | 现象 | 根因 | 修复 |
|---|---|---|---|
| 1 | ALU 测试第 2 项失败，寄存器读到旧值 | 寄存器堆同拍写读：相距 3 条指令的 RAW 未旁路 | 在 ID 级增加 `rf_we/rf_waddr` 旁路（WB→ID） |
| 2 | `csrw` 后紧跟 `csrr` 读到旧值 | CSR 读在 EX、写在 MEM，时序错位 | 冒险单元增加 CSR 写后读互锁（停 1 拍） |
| 3 | 排序结果降序 | 测试程序交换条件写反（`bge t1,t2` 应为 `bge t2,t1`） | 修正测试用例 |
| 4 | 编译后模块"消失"、仿真无输出 | Verilog 文件被写入 UTF-8 BOM，iverilog 遇 BOM 丢弃后续内容 | 去除 BOM，并在工程约定中禁止 BOM |
| 5 | `$readmemh` 未加载 | `parameter [1023:0]` 非字符串参数 | 改为无类型字符串参数 |
| 6 | xsim 报 timescale 不一致 | RTL 无 `` `timescale `` | 所有 RTL 文件补充 `1ns/1ps` |
| 7 | 加 Cache 后 I-Cache 缺失数 ≈ 循环次数（1037 次） | 分支重定向时中止未完成的行填充，导致同一行反复重填 | 移除"重定向中止填充"，缺失降为 15 次（仅冷缺失） |
| 8 | 外设访问被 D-Cache 误判为缺失 | Cache 未区分地址空间 | 仅 DMEM 段（`addr[31:16]==0x1000`）接入 D-Cache，外设旁路 |

## 5. 覆盖率讨论

- **指令覆盖**：RV32I 全部 37 条中的 36 条被 t01~t07 直接覆盖；`FENCE`/`FENCE.I`
  在 t02 中作为 NOP 执行验证（译码为 NOP，不改变体系结构状态）。
- **冒险覆盖**：EX/MEM 转发、MEM/WB 转发、WB→ID 旁路、load-use、store 数据转发、
  CSR 互锁、分支清空均有专项用例。
- **异常/中断**：4 类同步异常 + 1 类异步中断全部覆盖。
- **外设**：GPIO 寄存器、定时器计数/比较、UART 发送忙状态。

## 6. 已知限制

1. Cache 未实现关键块优先/非阻塞填充，缺失仍冻结 5 拍。
2. Cache 数据阵列采用 LUTRAM（组合读），容量再增大时会挤占逻辑资源。
3. 未实现 A/F/D/C 扩展；无 MMU/用户态（仅 M 模式）。
4. 分支预测为 BTB + 两位计数器，未做返回地址栈（RAS）与锦标赛预测。
5. DIV/REM 固定 32 拍，未做提前结束；高频除法场景开销较大。
6. 字/半字非对齐访问按"对齐字"处理，不产生异常（RV32I 编译器不会生成此类访问）。
7. 中断仅支持机器定时器（MTIP），未接外部中断控制器。

## 7. 综合评估（Vivado 2023.1，Artix-7 xc7a35t，仅供参考）

> 实际目标器件是紫光同创 PG2L200H，此处用 Vivado 仅做"可综合性 + 资源量级"检查。
> 综合时载入 CoreMark 镜像（定义 `SIM_INIT`），避免存储器内容被常量传播。

| 项目 | 结果 |
|---|---|
| 全 SoC（含 AI 加速器） | **10919 LUT**（6843 逻辑 + 4076 LUTRAM）/ **3726 FF** / **28 BRAM** / **20 DSP** |
| 10 ns 约束 | WNS = **-3.10 ns** ⇒ 估算 **≈76 MHz**（68% 为 OOC 布线估算） |
| 关键路径 | 19 级逻辑、无 DSP；逻辑延迟 4.0 ns、布线估算 8.6 ns |

**整行突发的实现过程（两轮迭代）**

1. 第一版只把 Cache 接口加宽到 128 位，存储器仍是 32 位阵列拼 4 字 →
   4 个读端口无法推断 BRAM，LUT 暴涨到 **57 495**，废弃。
2. 第二版把 **存储器本身** 改成 4096 x 128 位（16 字节使能写），Cache 数据阵列
   也改成"按行存储"（128 位/项，单写端口），BRAM 恢复正常：

| 方案 | LUT | FF | BRAM | 缺失代价 |
|---|---:|---:|---:|---:|
| 32 位单字读 | 6036 | 3120 | 31.5 | 5 拍 |
| **128 位整行（采用）** | **7828** | **3159** | **30** | **3 拍** |

代价是 +29% LUT（数据阵列 128 位宽、两读端口复制），换来缺失代价 5→3 拍，
t01 321→216（-33%）、t06 625→580、t10 16070→15260。

**调试记录**：字节使能最初写成 `{4{be}}`，会把 4 位 BE 复制到全部 16 个通道，
导致一次 32 位写改掉整行 4 个字；改为 `{12'd0, be} << {addr[3:2],2'b00}` 后修复。
该 bug 在 14 项汇编测试中未暴露（连续写覆盖了被污染的字），由 CoreMark 的
栈/bss 访问暴露。

## 8. 裸机 C 与 CoreMark

### 8.1 工具链

- `riscv-none-elf-gcc 14.2.0`（xPack），`-march=rv32im_zicsr -mabi=ilp32 -O2`
- 裸机启动：`sw/c/crt0.S`（设栈、清 bss、调用 main、写测试寄存器）
- 链接脚本：`sw/c/link.ld`（.text → 0x0，.data/.bss/.rodata → 0x1000_0000）
- 输出：`-O ihex` 后由 `sw/tools/hexsplit.py` 按地址拆成 imem.hex / dmem.hex

### 8.2 自研基准（bench.c）

筛法（256 以内 54 个素数）+ 16x16 矩阵乘 + CRC32 + 除法密集循环，
全部校验通过：**58667 拍 / 42784 条指令，IPC = 0.73**。

### 8.3 CoreMark 2K performance run

| 项目 | 结果 |
|---|---|
| 代码大小 | 3035 字（约 12 KB） |
| seedcrc | 0xe9f5（与官方一致） |
| crclist | 0xe714 |
| crcmatrix | 0x1fd7 |
| crcstate | 0x8e3a |
| crcfinal | 0xe714 |
| 1 次迭代计时区 | 357,397 拍 |
| 2 次迭代计时区 | 701,416 拍（每次 350,708，偏差 0.06%；乘法移入 MEM 前） |
| 整程序 | 453,652 拍 / 388,324 条指令，IPC = 0.86 |
| 折算性能 | **≈2.80 CoreMark/MHz** |

说明：EEMBC 规定单次运行需 ≥10 秒，仿真下无法满足，因此以官方 CRC 值作为
功能正确性的判据，性能按 `mcycle` 拍数折算（`CoreMark/MHz = 1e6 / ticks`）。

## 8b. 边缘 AI 加速（MNIST）

| 项目 | 结果 |
|---|---|
| 模型 | 196-32-10 MLP（14x14 下采样），INT8 权重 |
| 量化精度（Python 仿真，10k 测试集） | float 96.26% / INT8 96.19% |
| RTL 仿真（20 张图） | **19/20 = 95%** |
| 整程序周期 | 170,691 拍（20 张图，含一次权重装载） |
| 单帧周期 | 约 6.5k 拍（8 组 FC + 3 组 FC + 归约） |

**加速器结构**：`0x2000_4000` 控制寄存器 + `0x2000_8000` 8 KB 缓冲；
FC 每拍 4 个 INT8 MAC，RELU/ARGMAX 硬件完成；偏置折进额外一行权重。

**资源增量**：AI 加速器约 +3.1K LUT（其中 8 KB 缓冲按 LUTRAM 实现占 ~2K）与 +8 DSP；
若要进一步省面积，可把缓冲改成同步读 BRAM（引擎改为两拍读写）。

**调试记录**

| 现象 | 根因 | 修复 |
|---|---|---|
| FC 跑满 200 拍但结果为 0 | AI 缓冲 8 KB 跨 `0x20008/0x20009` 两个 4 KB 页，译码只匹配前者，偏移 ≥4 KB 的写入丢失 | 译码改为 `addr[31:13]==19'h10004` |
| 启动后立刻轮询读到旧 done | `done` 是粘滞位，软件读早于状态机清零 | 启动后插入 8 个 nop，再按 busy→done 顺序等待 |
| 最初 INT8 精度仅 65% | 激活量化用固定右移，饱和严重 | 改为按校准集定点缩放 `(y*M)>>15`，精度回到 96% |
